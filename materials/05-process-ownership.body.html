5.1　先确定谁拥有状态

同名 step 容易造成误解。LLMEngine 位于客户端一侧，负责接收输出和用户结果处理；EngineCore 管理请求调度和资源决策；Executor 把本轮工作分发给执行端；Worker/ModelRunner 持有设备模型、输入缓冲与物理缓存。具体实现可采用 in-process 或多进程路径，因此职责边界与 OS 进程边界应分别核实。

层次典型状态不能据此假定

5.2　请求进入与输出返回

离线入口完成输入准备并添加请求，客户端反复等待输出，直到自己的未完成请求结束。EngineCore 在独立的执行循环里推进 Schedule→Execute→Sample→Update；客户端的一次 get_output 可能收集多个请求的输出，一次客户端 step 并不必然对应一次设备 forward。

阅读 EngineCoreClient 时先找到工厂如何选择客户端类型，再区分 InprocClient 与多进程 client。多进程路径有请求和输出消息通道；传输的是请求/执行元数据与结果，不等于在客户端调用设备进程内的同名 Python 方法。对象序列化、传输缓冲、唤醒与队列等待也可能产生 CPU 成本。

例题 5.1　三次输出为什么不等于三个直接调用

教学请求 R 在客户端提交；引擎完成 Prefill 产生 y₁，随后推进两次 Decode，形成 y₂、y₃。客户端输出 processor 若累计输出，则第三次接收可呈现 y₁y₂y₃；若增量输出则只呈现新片段。不能从最终文本长度推断 IPC 消息数、客户端 step 次数或模型执行次数。

应在图中单独画请求通道、执行计划、模型结果与用户输出通道，再标出每个对象的生产者/消费者。时间戳必须写观察位置，跨进程时间做差先确认时钟基准。

概念检查：设备 KV 是 Tensor，调度器为何只持有块 ID？

调度器决定资源与逻辑位置，执行端用块表把位置映射到设备 cache。传块 ID 与 token 数比传整个 KV 张量成本小，也保留设备执行的状态归属。

5.3　完成、取消和异步 future

请求完成需要三类状态收尾：用户侧停止输出，引擎侧移除活动请求并处理缓存引用，Worker 侧移除持久 batch 状态。前缀缓存开启时释放请求引用不一定擦除缓存内容，也不一定减少设备预分配池。取消在设备执行中到达时，已提交 kernel 不一定立刻停止；正确性依赖引擎在安全边界处理 abort 与后续结果。

t_request = t_input + t_queue + t_execution + t_output （分项边界需一致）(5.1)

式 5.1 是用于追踪的串行概念分项，不保证实际并行系统各项简单相加。future.result() 是等待结果的一个边界；如果多个执行批次重叠，CPU 调度时间与设备时间可能部分覆盖。后续第 9 课会分析异步调度的收益条件。

完成后展开：必做题参考推理

2. 逻辑资源决策在 Scheduler/KV 管理；物理张量与执行映射在 Worker/Runner。
