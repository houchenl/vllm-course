1.0　问题、目标与学习路线

你接到一项适配任务：模型能启动，但首 token 很慢；输入变长后吞吐下降；迁移到 910C，性能排序又发生变化。应该先调哪个参数？仅凭“模型能运行”无法回答。你需要知道，一次请求究竟计算了什么、保存了什么状态、经过了哪些进程，以及测量的时间包含哪些工作。

本章建立后续学习共用的分析模型：输入 token → 模型计算 → 历史状态 → 采样 → 下一次计算。随后把这个模型映射到 vLLM 的客户端、调度器和设备执行路径。你熟悉 Transformer，因此本章从推理中的状态和时间入手，Attention 的训练推导不作为前置复习任务。

学习目标 / LEARNING OBJECTIVES
  1. 解释第一个输出 token 为什么来自 Prefill，以及一个输出 token 何时拥有自己的 KV。
  2. 在明确假设下推导 KV 容量，检查单位，并区分逻辑状态、分页槽位和设备预分配池。
  3. 区分 TTFT、TPOT、ITL、端到端延迟和批次吞吐，判断一项测量能支持哪些结论。
  4. 定位五个源码方法，画出跨进程的数据流和引擎内的调度闭环。
  5. 在一个已验证的单卡环境建立四组基线，提出一个可检验的性能假设。

1.1　先建立一个可推演的模型

工程分析需要一个足够简单、又能保留关键因果关系的起点。本章先采用标准 decoder-only 自回归模型：所有相关层使用全因果 Attention；没有前缀缓存命中，没有投机解码，一次分析一个序列。第 1.8 节再说明你的两个工作模型如何超出这些假设。

设输入序列为 x1, …, xP，模型处理这些输入位置，并从最后位置的 logits 中选择第一个输出 y1。这次对输入前缀的处理称为 Prefill（预填充）。因果 mask 使每个位置只能看到允许的历史；矩阵运算仍可一起处理多个输入位置。

为了生成 y2，再把已经选择的 y1 作为新输入送入模型。模型读取历史状态、计算新位置，然后选择下一个输出。后续逐步生成称为 Decode（解码）。这里“选择”既可以是 greedy，也可以是其他采样策略；本节只讨论两次模型计算之间的数据依赖。

关键区别 / THE KEY DISTINCTION

已知 token 的值，与已计算该 token 的 KV，是两件事情。采样产生的是一个 token ID。只有把这个 ID 再输入后续 forward，模型才计算它在相应层的 K/V。

表 1.2　标准完整 Prefill 与普通 Decode 的状态变化。
计算本次输入计算后的逻辑 KV新输出
Prefillx₁ … xPx₁ … xPy₁
第一次 Decodey₁x₁ … xP, y₁y₂
第二次 Decodey₂x₁ … xP, y₁, y₂y₃

因此，在上述流程中生成 N 个输出，需要一次完整 Prefill 加 N−1 次普通 Decode。刚得到最后一个输出时，已计算的历史通常有 P+N−1 个位置。这个计数描述模型计算依赖；Chunked Prefill 会把 Prefill 拆成多个执行批次，投机解码会改变一次迭代的输入输出量，lookahead 也可能提前分配槽位。模型步骤数不能直接代替实际调度次数或物理分配量。

概念检查 1.1：生成 32 个输出，是否需要 32 次普通 Decode？

按本节假设，需要 31 次普通 Decode。第一个输出已经由完整 Prefill 产生。若实际引擎把 Prefill 分块或采用投机解码，必须另行统计执行批次，不能套用这个次数。

1.2　KV cache 是计算与存储之间的交换

对一层标准 Attention，设 X 为本次需要计算的位置的输入表示。线性投影得到 query、key 和 value：

Q=XWQ,K=XWK,V=XWV(1.1)

query 根据与 key 的相关性分配权重，再对 value 加权：

Attention(Q,K,V)=softmax(QKTdh+M)V(1.2)

dh 是每个 head 的维度，M 是因果 mask。Decode 的新 query 需要历史位置的 K/V；历史 K/V 在这些位置的输入和模型参数不变时可以复用。因此，缓存过去算出的 K/V，就无需每次生成都重新执行整个前缀的模型计算。

在 Decode 中，式 (1.1) 可以只为新位置计算投影；式 (1.2) 的 K/V 则组合历史缓存与新位置。缓存减少重复计算，却带来需要分配、读取、共享和回收的持续状态。缓存管理于是成为引擎设计的核心，而非模型旁边的一项可有可无的优化。

表 1.3　容量分析应区分的四类对象。
对象作用生命周期
模型权重定义线性层、Attention、专家等参数模型驻留期间
请求 KV / 状态复用历史推理状态请求存活或缓存复用期间
激活与 workspace本次计算的输入、中间结果和临时空间一个或若干执行步骤
Graph 与运行时资源执行捕获、通信、内存管理等引擎运行期间

KV cache 不等于权重，也不等于永久保存所有中间激活。一个模型还可能保存专用压缩表示或递推状态；到混合架构时，必须逐层确认“究竟缓存了什么”。PagedAttention 原论文讨论动态 KV 的碎片和共享问题；第 7–8 周将把这些问题落实到块表、引用计数和源码。

1.3　从一个元素推导 KV 容量

容量公式不应从记忆开始，而应从缓存中的元素开始。一个位置在一层有 Hkv 个 K heads 和同样多的 V heads；每个 head 有 dh 个元素，每个元素占 s 字节。乘以所有相关层，再乘以保留的位置总数，就得到理想存储量。

适用条件 / ASSUMPTIONS

以下公式假设：L 层均为标准全 Attention；每层 K/V 的 heads、维度和精度相同；没有跨请求共享，没有 TP/CP 分片，没有压缩或窗口淘汰。它估算缓存载荷，不包含元数据、对齐、预留槽或整池预分配。

表 1.4　符号与单位。
符号意义单位
LAttention 层数层
Hkv每层 KV heads 数head
dh每个 K/V head 的维度元素
s每个缓存元素的字节数byte / 元素
Ti请求 i 当前保留的已计算位置数token
MKV=2×L×Hkv×dh×s×∑iTi(1.3)

系数 2 代表 K 和 V。GQA（Grouped-Query Attention，分组查询注意力）让多个 query heads 使用较少的 KV heads，所以这里使用的是 KV heads 数。同样，要优先读取配置中的显式 head_dim；hidden_size / num_attention_heads 只有在具体模型满足该关系时才成立。

例题 1.1　标准教学模型的容量

已知。 L=32，Hkv=8，dh=128，KV 使用 BF16，因此 s=2 byte。8 个请求各保留 4096 个已计算位置。

建模。 先求一位置跨所有层的缓存，再乘所有请求的位置数；采用式 (1.3) 的全部假设。

每 token KV = 2 × 32 × 8 × 128 × 2
             = 131072 byte = 128 KiB
总 KV        = 128 KiB × 4096 × 8 = 4 GiB

检查。 每项计数都应为无量纲的数量，s 提供字节单位。1 KiB=2¹⁰ byte，1 GiB=2³⁰ byte；这里没有使用十进制 GB。

工程解释。 在假设不变时，请求数翻倍会让理想 KV 翻倍，KV heads 从 8 降至 1 会让理想 KV 降至八分之一。实际架构改变后，需要重新检查假设。

分页带来的第二种容量

缓存通常按块分配。设块大小为 b token，一个请求保留 Ti 个位置，则至少需要 ⌈Ti/b⌉ 个块；最后一块可能只填了一部分。各请求独立分配且无共享时，槽位近似为：

Sslots=∑i⌈Tib⌉×b(1.4)

例题 1.1 若每请求改为 4097 个位置，且教学块大小 b=16：理想载荷约为 4.00098 GiB；每请求分配 4112 个槽位后，取整载荷为 4.015625 GiB。差值来自块内空槽，仍未包括真实 backend 的对齐、分组、元数据和预留。

例题 1.2　用真实 config 检验直觉

已知。 Qwen3-0.6B 官方配置给出 L=28、Hkv=8、head_dim=128。假定运行时 KV 为 BF16，4 个请求各保留 1024 个位置。

每 token KV = 2 × 28 × 8 × 128 × 2 = 114688 byte = 112 KiB
总 KV        = 112 KiB × 1024 × 4 = 448 MiB = 0.4375 GiB

检查。 该配置的 hidden_size=1024、query heads=16；1024/16=64，却不等于显式 head_dim=128。因此，仅凭 hidden_size 反推 head_dim 会把这个例子的缓存低估一半。

工程解释。 理论使用官方配置，运行结论使用实际 checkpoint revision、有效配置与 KV dtype。模型名称本身不构成容量参数。

1.4　“权重能装下”为什么不够

设一个模型有 7×10⁹ 个实际驻留参数，全部 BF16。原始权重需要 14×10⁹ byte，约 13.04 GiB。若再加例题 1.1 的 4 GiB KV，已经约为 17.04 GiB，激活、workspace、Graph 和通信资源尚未计入。对 MoE 而言，每 token 激活的参数量反映部分计算工作，不能代替总驻留权重来估算设备容量。

Mpeak≈Mweights+MKV/state+Mactivation/workspace+Mgraph/runtime+Mmargin(1.5)

式 (1.5) 是分项规划模型，各项可能共享或复用内存，最终需要峰值实测。容量分析的任务，是解释“哪些资源随模型、长度、并发和执行配置变化”，再为测量提供可检验的估算。

vLLM 还可能预先分配较大的 KV 池。一个请求完成后，其块变为可回收或可复用，但设备预分配池未必缩小。因此应区分三个量：请求当前的逻辑状态、请求分配的物理块、引擎拥有的缓存池。设备工具显示的占用不能直接当成活跃请求 KV 载荷。第 7 周将追踪这些量各由哪个对象管理。

概念检查 1.2：请求结束后设备占用没有下降，能否直接判断内存泄漏？

不能。引擎可能保留预分配池，缓存也可能为前缀复用保留块。应核对可用块、引用计数、运行时保留内存及重复负载中的增长趋势。设备占用是线索，尚不足以确定泄漏。

1.5　从工作量提出性能假设

Prefill 和 Decode 使用相同的模型权重，却有不同的输入组织。Prefill 一次带来多个新位置，线性层可以形成较大的矩阵操作；普通 Decode 每个请求每步只带来一个新位置。小 batch 下，后者能分摊权重读取和设备调用的工作较少。增大 batch 可能增加复用，也会增加缓存需求和一次执行的工作量。

对本章的全 Attention 模型，Prefill 的注意力部分随 prompt 长度近似呈平方增长，普通 Decode 的注意力部分随保留历史长度增长。这个判断只涉及注意力部分：线性层、MoE、窗口、压缩、稀疏索引、硬件布局和通信都会改变全模型的成本。

从推断到证据

“小 batch Decode 可能受到权重带宽或启动开销影响”是有机制依据的假设。“Prefill 一定算力受限、Decode 一定带宽受限”不是可直接采用的结论。判断瓶颈还需要长度、batch、实际 kernel、通信与 profiler 的证据。

本周只练习把现象转成问题：输入变长增加了哪部分计算与状态？batch 增加能复用什么，又引入什么等待？设备变多增加了什么容量，也带来什么通信？第 3 周用 Roofline 和算术强度把这些问题量化，第 12–13 周再追踪 TP 的实际代价。

1.6　先定义时间边界，再讨论快慢

设 t₀ 为请求开始时间，t₁ 为第一个输出 token 的观察时间，tN 为最后一个输出 token 的观察时间，tdone 为请求完成时间，N 为实际输出 token 数。明确同一观察位置后，可以定义：

表 1.5　指标的数学含义与解释边界。
指标定义回答的问题
TTFT
Time to First Token		t₁ − t₀多久能看到第一份输出？客户端口径通常还包含网络、处理和排队。
TPOT
Time per Output Token		(tN − t₁) / (N−1)，N>1首 token 后，平均多久产生一个后续 token？
ITL
Inter-Token Latency		tj − tj−1，j≥2相邻输出之间的间隔是否平稳？
E2E
End-to-End Latency		tdone − t₀整个请求多久完成？
聚合输出吞吐窗口内输出 token 总数 / 窗口时长系统在该窗口完成了多少输出工作？

若 N=1，TPOT 在上述定义下没有分母；某些实现用 0 占位，不能把它理解为零生成成本。若流式协议一次 chunk 携带多个 token，chunk 时间戳也不能还原 chunk 内逐 token 的生成时刻。报告必须说明观察的是 token 事件还是 chunk 事件。

本地 metrics/stats.py 的平均输出 token 时间使用首个到最后一个生成事件，分母排除第一个 token。客户端 benchmark 的边界仍需单独核对。TTFT 不等于 Prefill kernel 时间，因为请求进入、排队、数据处理和输出传递也可能被包含。

本周测量口径

离线 LLM.generate 等整个批次完成后返回。本课脚本测量批次 wall time，并用批次实际输出数除以它，得到聚合输出 token/s。该时长包含 Prefill、Decode 和调用端输出处理。脚本没有逐请求首 token 或逐 token 时间戳，因此不能报告流式 TTFT、ITL，也不能把总耗时除以输出长度称为纯 Decode 速度。

概念检查 1.3：总 token/s 增加 50%，是否意味着用户等待时间缩短？

不能。更大的 batch 可能使系统同时完成更多输出，同时增加每次执行和排队时间。需要同时观察单请求 TTFT、后续 token 间隔、E2E 和负载条件。吞吐与延迟回答不同问题。

1.7　把模型映射到 vLLM V1

模型定义计算规则，引擎决定当前执行哪些请求、为它们安排多少 token、怎样管理缓存，并把结果送回调用端。一次请求的执行因而跨越两个层次：模型内部的张量运算，与引擎维护的请求和资源状态。

读出闭环，而不迷失在分支里

从 EngineCore 的普通 step 路径摘出以下短片段。它省略 grammar、abort、日志等分支，只作为阅读提示，不能替换真实实现：

scheduler_output = self.scheduler.schedule(self._should_throttle_prefills())
future = self.model_executor.execute_model(scheduler_output, non_block=True)
# …… grammar 与其他处理 ……
model_output = future.result()
if model_output is None:
    model_output = self.model_executor.sample_tokens(grammar_output)
engine_core_outputs = self.scheduler.update_from_output(
    scheduler_output, model_output
)

schedule 决定本次执行内容；Executor 发起执行并返回 future；获得模型结果后，必要时通过专用路径采样；最后由 Scheduler 更新请求与缓存状态。新输出改变了下一轮需要计算的内容，闭环由此继续。第 9 周再对照 batch queue 和 async 路径。

源码事实：同名 step，职责不同

当前本地 LLMEngine.step() 通过 engine_core.get_output() 接收输出，再交给 output_processor；它没有直接调用 EngineCore.step()。EngineCore 在自己的执行循环里推进工作。因此，客户端反复 step 与引擎反复 step 通过数据流关联，不能画成跨越 IPC 的直接 Python 调用栈。

用统一 token 进度理解 Prefill 和 Decode

Scheduler 开头的注释强调两种进度：num_computed_tokens 表示计算进度；num_tokens_with_spec 表示包含 prompt、输出与投机 token 的目标进度。调度器为请求安排 token，让计算进度追上目标，受本轮资源预算约束。因此，Prefill 和 Decode 是推理概念，但调度代码可以采用统一表达。

例题 1.3　128 个输入位置如何变成一个待计算位置

无前缀命中时，初始 prompt 有 128 个位置需要计算。完整 Prefill 后，计算进度到 128，同时采样出 y₁；已知输入与输出共 129 个 token，下一轮通常需要计算 y₁ 这个位置。这里同一种“目标进度减计算进度”的描述，先覆盖多个输入 token，又覆盖一个新输出 token。实际字段何时更新、是否加入预留或投机状态，第 6 周再逐项追踪。

本周在报告中填一张方法职责表：所在进程、输入对象、输出对象、主要状态、下一跳。特别标出“安排 token”和“运行模型”分别属于谁。更多入口见源码地图，本周无需展开所有代码组。

1.9　实验：从可核对的估算到可复现的基线

本周实验回答两个问题：容量推导是否与逐项计算一致？在固定软件栈和小模型下，只改变输入长度或批次请求数，会观察到怎样的批次耗时与聚合吞吐？前者验证算术和假设，后者建立运行事实。两者不相互替代。

120 分钟建议分为环境记录 25 分钟、估算核对 15 分钟、基线运行与分析 60 分钟、数据整理 20 分钟。使用已有验证镜像和空闲单卡；复杂安装问题计入预算，必要时把设备实测顺延，并保留为待完成。

实验 A　不使用加速器的容量核对

容量脚本仅使用 Python 标准库。以下命令从 Linux 的课程目录执行；Windows 对应使用 .venv\Scripts\python.exe。

uv venv .venv
.venv/bin/python labs/lesson01_estimate.py
.venv/bin/python labs/lesson01_estimate.py --tokens 4097
.venv/bin/python labs/lesson01_estimate.py --layers 28 --kv-heads 8 \
  --head-dim 128 --tokens 1024 --requests 4

三个结果应分别核对到：每 token 128 KiB 且理想 KV 为 4 GiB；4097 位置的取整载荷为 4.015625 GiB；Qwen 示例为 0.4375 GiB。再手算 KV heads 从 8 到 1，以及请求数从 8 到 16 的变化，说明前提和倍率。

实验 B　记录真实运行栈

本周先完成 H20 或 910C 中最方便的一个平台；910B 是补充平台。你报告 vLLM 0.31.0 与 vLLM-Ascend 0.30.0rc1，Ascend 配套版本表把 0.30.0rc1 对应到 vLLM 0.30.0。因此需要分别读取 NVIDIA 与 Ascend 镜像内的实际包版本，不能推定两者相同。

在独立学习目录创建继承镜像已安装依赖的环境。将解释器路径替换为该已验证镜像实际使用的 Python，以保持相同 ABI 和软件栈。

uv venv --system-site-packages --python /path/to/validated/python .venv
.venv/bin/python -c 'import importlib.metadata as m; import sys; print(sys.version); print({n: m.version(n) for n in ("vllm", "torch", "transformers")})'
.venv/bin/python -c 'import torch; print("torch CUDA runtime:", torch.version.cuda)'

Ascend 镜像另行记录插件、torch_npu、设备和 CANN：

.venv/bin/python -c 'import importlib.metadata as m; print({n: m.version(n) for n in ("vllm", "vllm-ascend", "torch", "torch-npu")})'
npu-smi info
cat /usr/local/Ascend/ascend-toolkit/latest/version.cfg

CANN 的安装路径可能随镜像变化；文件不存在时读取实际 toolkit 路径或安装清单。NVIDIA 用 nvidia-smi 记录设备和驱动，必要时用 nvcc --version 记录安装的 toolkit。nvidia-smi 的 CUDA Version 表示驱动支持的版本，不能用它替代 PyTorch 运行时或镜像内 toolkit 的安装版本。参见NVIDIA 官方说明。

阅读版本与运行版本

当前本地阅读仓库已核对 Git commit 与所选文件指纹，见 阶段 A 源码记录；原始指纹单独保留。Ascend 主线的 vllm-main-verified.commit 是插件指定的配套目标，当前 vLLM 阅读提交与该配套目标不同，不能默认共同运行。阅读定位与运行日志必须分别记录，版本差异本身也是适配证据。

实验 D　把结果写成可以反驳的解释

先报告观察，再提出机制，最后说明缺失的测量。例如：“B 的中位聚合输出吞吐高于 A；可能因为权重复用或调用开销摊薄；需要 profiler 区分两种机制。”这里吞吐变化是观察，原因是待验证假设，两者在报告中应有不同地位。

若 C 比 A 耗时更长，差异可能同时来自 Prefill 和后续更长的历史 KV 访问。两者之差不能直接称为纯 Prefill 时间。三次重复适合本课初步比较，不能支持可靠的 P95/P99 或生产稳定性结论。没有出现预期趋势时，同样记录波动、其他负载与下一项测量。

提交的数据与分析

提交实际环境版本、命令和有效配置、四组原始数据、批次时长与聚合吞吐的中位数，以及一个假设和它需要的验证。学习投入和机器后台运行时间分开记录。当前讲义没有填入任何硬件性能结果。

1.10　习题、参考解答与通过标准

先关闭参考解答，在纸上或报告中完成必做题。解释题应包含因果关系和适用条件；源码题应指出实际方法；数字题应写单位。选做题用于你已有工作案例的延伸，不增加本周必修预算。

必做题 / CORE PROBLEMS

  1. 请求轨迹。 P=128、N=32，按 §1.1 的假设，首输出来自哪次计算？最后输出刚采样时有多少已计算位置？为什么？
  2. 容量推导。 重算例题 1.1 和 1.2，解释为何使用 KV heads。若请求长度不同，应怎样修改公式？
  3. 容量诊断。 一个 MoE 模型的激活参数很少，但设备仍放不下。给出需要检查的内存项，说明激活参数为何不足以估算驻留权重。
  4. 源码边界。 LLMEngine.step 是否直接调用 EngineCore.step？指出本地证据，并标出图 1.6 中的请求和输出通道。
  5. 调度状态。 用 128-token prompt 和刚生成的 y₁，解释统一 token 进度如何覆盖 Prefill 与 Decode。区分概念轨迹和精确字段更新时间。
  6. 测量设计。 为什么本课离线脚本不能报告流式 TTFT？若要验证“batch 越大用户越快”，还需要哪些数据？
  7. 架构边界。 为什么不能直接用式 (1.3) 估算两个工作模型的全部缓存？各指出一个本地实现线索。

选做题 / TRANSFER PROBLEMS

  1. 例题 1.1 的 8 个请求分别保留 1024、2048、3072、4096、1024、2048、3072、4096 个位置。计算理想 KV，解释为什么统一按最长长度估算会高估活跃载荷。
  2. 若输出到达时间为 125、145、175、185、205 ms，计算 TTFT、四个 ITL 和 TPOT。平均值隐藏了哪一种波动？
  3. 设计一个下一阶段实验，用来区分“小 batch 下权重读取较贵”和“设备调用开销较贵”。写出希望从 profiler 看见的证据，不要求本周完成实测。
完成后展开：必做题参考解答与推理

1. 完整 Prefill 处理 prompt 最后位置并采样 y₁。31 次普通 Decode 产生其余输出，最后采样时已计算 128+31=159 个位置，y₃₂ 尚未再次输入模型。分块、投机和物理预留须另行考虑。

2. 例题 1.1 为每 token 128 KiB、总量 4 GiB；例题 1.2 为每 token 112 KiB、总量 448 MiB。GQA 的 K/V 存储由 KV heads 决定。不同长度使用 ΣTᵢ；物理独立分页时使用 Σ⌈Tᵢ/b⌉b。

3. 检查总驻留权重、缓存/状态、激活与 workspace、Graph/通信运行时资源和余量。路由只选择部分专家参与一个 token 的计算，未参与本 token 的专家参数仍可能驻留设备。

4. 当前 LLMEngine.step 调用 engine_core.get_output，再做 output_processor 处理；EngineCore 在独立执行循环里调度并运行模型。数据通道跨越职责与进程边界，同名 step 不构成直接调用关系。

5. 初始多个 prompt 位置待计算，完整 Prefill 后新输出 y₁ 使目标比已计算进度多一个位置。统一进度差可覆盖两类负载；更新顺序和投机状态以 Scheduler 实现为准。

6. generate 返回完成后的批次结果，脚本只记录调用前后的时间，没有第一份输出或逐 token 的事件。还需流式逐请求 TTFT、ITL/TPOT、E2E，以及一致的并发/到达率、长度和缓存条件。

7. DeepSeek 本地包含 sparse_mla、压缩/稀疏与 decoder replay 路径；GLM common/model 按 layer_types 区分 KDA/MLA。应逐层、逐缓存平面分析状态、dtype 和分片，式 (1.3) 的全层相同 K/V 假设不成立。

选做题与诊断参考要点

8. 位置数为 20480，总载荷=128 KiB×20480=2.5 GiB。统一按最长长度会算成 4 GiB；物理预分配或保留容量又是另一口径。

9. TTFT=125 ms，ITL=20、30、10、20 ms，TPOT=20 ms。平均值掩盖了后续生成的不均匀间隔。

10. 可固定模型、长度和 eager 配置扫描 batch，同时观察 kernel 间隙、主机提交时间、各 kernel 时长及内存带宽指标。仅看总吞吐不足以区分原因；带宽瓶颈要用实际访问量和可达到带宽判断。

诊断。 8×1024×4096×2=67108864 byte=64 MiB。transpose 通常返回改变 stride 的 view，后续 contiguous 或算子路径可能触发复制。设备 API 的主机返回可能早于设备完成；TP 的切分与通信要追踪具体层实现。权重以外还有其他内存项；聚合吞吐不能直接证明请求更快。
