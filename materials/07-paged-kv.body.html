7.1　逻辑连续不要求物理连续

请求看到的是位置 0、1、2…的连续历史。分页管理把历史分成固定大小的逻辑块，每个逻辑块由块表指向某个物理块。物理块可分散在池中，Attention kernel 根据块表访问它们。因此，分页组织解决动态容量与共享问题；它本身不说明 Attention 计算是否采用 FlashAttention。

logical_block = floor(t / b)；in_block = t mod b(7.1)
slot = block_table[logical_block] × b + in_block(7.2)

t 为从 0 开始的逻辑位置，b 为每块 token 数，slot 是抽象 token 槽位索引。真实 Tensor 地址还依赖 KV layout、head、层、dtype、分组与 backend；不能把 slot 直接当所有模型的字节地址。

例题 7.1　位置 9 写到哪里

教学 b=4，块表为 [7,2,9]。t=9 属于逻辑块 floor(9/4)=2，块内偏移1，对应物理块9，槽位为9×4+1=37。逻辑相邻位置7和8分别可能落到物理块2和9，仍由块表维护因果历史。

7.2　分页尾块、共享与池容量

n_blocks = Σᵢ ceil(Tᵢ / b)；tail_slots = n_blocks × b − Σᵢ Tᵢ(7.3)

式 7.3 假设所有请求独立，无共享和额外预留，Tᵢ 是需要保留的位置数。共享时要统计唯一物理块，不把多个请求引用重复计入；lookahead、对齐、混合分组和压缩表示另算。

例题 7.2　三个不等长请求

教学 T=[5,8,9]、b=4，每 token 跨层载荷1 KiB，池共10块。独立请求需要2+2+3=7块，分配28槽，逻辑22槽，尾块空6槽。逻辑载荷22 KiB、分配载荷28 KiB、预分配池40 KiB。三种数值回答不同问题。释放5位置请求后，它的2块可重新分配，但池的40 KiB可继续驻留。

分页可减少必须预留整条最长序列的浪费，但它仍有尾块空槽、块表、对齐和分派成本。更小块并非总是更快：块数和元数据增多，kernel 访问、hash 和管理开销也会变化。课程不建议在第一轮直接调整未知 backend 的 block size。

7.3　分配与释放发生在哪一层

KVCacheManager 对请求提出所需块数量，协调器管理不同缓存组，BlockPool 提供可用块。执行端把 block ID 更新到持久块表，再按 slot_mapping 写设备 cache。请求完成释放逻辑引用；缓存哈希可能保留以便以后命中。

在前缀缓存下，“可重新分配”与“没有可读缓存内容”不是一回事：引用为0的块可以仍带缓存哈希，进入可回收队列；被重新分配时需要处理旧哈希。物理池、PyTorch allocator 保留量和设备工具总占用是不同指标。判断泄漏应观察重复稳定负载的增长趋势、活动引用与可用块，而非只看结束后显存是否下降。

概念检查：两请求有同样前三个逻辑块，就必然只占三块吗？

不必。要核实它们是否真的共享物理块、哪些块是完整有效前缀、是否有私有后缀和额外预留；逻辑内容相同不是分配证据。
