8.1　可以复用的是计算身份，不只是文本

Automatic Prefix Caching（APC，自动前缀缓存）复用已计算的历史状态。相同文本必须经过同样 tokenization、模板和配置，才可能拥有相同 token 前缀。LoRA、媒体输入身份、cache salt 等额外条件也可进入缓存键，防止不等价状态错误共享；实际键组成以本地实现与运行配置为准。

hⱼ = Hash(hⱼ₋₁, tokens_in_blockⱼ, extra_keysⱼ)(8.1)

链式哈希让当前块的身份依赖前面的历史，而不只依赖本块 token。相同后缀置于不同前缀下，其因果表示通常不同，不能仅靠块内 token 判断缓存相同。标准入门路径复用完整块；本地还有混合模型与更细的缓存扩展，因此不把这条简化规则宣称为全部主线实现。

例题 8.1　最后一个 prompt 位置为什么可能仍需计算

教学 b=4、prompt长度12且完整内容在缓存中。当前 KVCacheManager.get_computed_blocks 使用 prompt_length−1 的上界，因为还需重算最后位置以取得 logits；块对齐使最大完整命中长度为 floor(11/4)×4=8，因此可能重新计算最后4位置，而非仅1位置。对于 prompt长度13，命中上界12，可复用前三个完整块并计算第13位置。

这是所选普通路径的源码事实，不推广到任意池化、logprob、混合状态或专用执行组合。复用 KV 不等于复用最终用户输出或最后位置 logits。

8.2　引用为零不表示立刻删除内容

表 8.2　共享前缀的引用轨迹，忽略其他引用。
事件两共享块 ref_cnt可回收性
A 使用缓存块1仍活跃，不能按空闲覆盖
B 命中并 touch2两个请求都引用
A 结束1B 仍活跃
B 结束0可作为回收候选，哈希可能仍保留
被其他内容重新分配新引用旧键应失效，不能再指向新数据

touch 增加引用，必要时从 free queue 移出；free_blocks 减少引用，到0后返回适当队列；再次分配涉及旧哈希失效。共享的完整已缓存块不应被普通后缀写入覆盖。可写性、copy-on-write、外部读者和多池路径是更复杂的边界，修改时必须逐一核对，不能只改 ref_cnt。

检查：B 的 token 前缀相同却未命中，必然是哈希坏了吗？

不必。可能尚未计算/完整缓存、已被回收、缓存关闭、cache salt/LoRA/媒体键不同、logprob路径跳过、或不同缓存组不满足复用条件。

8.3　缓存的收益模型与错误对照

Δt ≈ avoided_prefill_work_time − lookup / management_overhead(8.2)

该式仅解释有收益的方向。缓存不消除剩余后缀的计算，也不消除 Decode 对历史的读取。高命中率若定义为查询 token 比例，并不保证相同的请求加速比例；排队、Decode 长度和请求分布可占主导。首次请求同时触发编译和权重/cache预热时，首轮与第二轮差异混合了多个因素。

例题 8.2　冷热对照需要第三种条件

教学实验设置 APC关闭、APC开启但冷前缀、APC开启且相同前缀热命中三类条件。每个配置都先用不属于目标前缀的负载预热，再记录目标前缀的首次与重复请求。冷条件用独立学习服务重启/确认清空缓存，热条件在同一服务保持前缀和seed；如果全输入相同，应在报告里说明这比业务共同前缀更理想。

.venv/bin/python labs/stage_a_mechanisms.py prefix

.venv/bin/python labs/lesson08_prefix.py --model course-dense --tokenizer /models/Qwen3-0.6B --cache-condition enabled-fresh --output records/l08-apc-run01.json
# 重启独立服务、关闭APC后，用相同负载复现：

服务改为 --enable-prefix-caching；APC关闭的对照保留第四课设置。专用客户端先用无关前缀预热，再发送目标前缀首次请求和三次相同前缀请求，以及一个改变前缀的负对照；不会偷偷发送目标测试请求。它不重启/清空服务，也不能证明enabled-fresh是真冷，实际APC开关与缓存状态必须由你记录。通用benchmark可能预先发送测试请求，因此不直接拿它的首轮称作APC冷测。
